# September 2026 AI Hands-on Summary

note · AIさわってみ録 · 2026-10-18

September 2026 AI Hands-on Summary
September 2026 (September 1st to September 30th) was a month where the infrastructure for operating AI agents within an organization—while maintaining control over costs and permissions—was refined. In Claude Code, adjustments to permissions, such as the withdrawal of read-deny rules and command-level network permissions, progressed in parallel with operational improvements like cost display, caching, and gateway integration. Meanwhile, reports of attacks targeting AI agents and follow-ups on incidents caused by the agents themselves continued, with particular focus on questioning whether "human approval" and "isolation" are truly effective. Additionally, in BigQuery and data infrastructure, graph analysis and testing features reached GA, while in the model space, Claude Opus 5.5 and GPT-6 Sol/Luna aligned on the "same level for a lower price" trajectory. This month, I will organize the summary into six themes: Claude Code permissions and sandboxing, Claude Code cost and gateway operations, attacks and incidents targeting agents, agent control and data protection design, BigQuery and data infrastructure, and models and third-party CLI agents.
Adjustments to Claude Code Permissions and Sandboxing
- Withdrawal of Read deny: In v2.1.260, the change from the previous v2.1.259, which applied Read() deny rules to Bash arguments, was withdrawn. This was because rules like Read(./**/build/**) were blocking normal commands like npm run build, causing them to wait for approval even in auto mode. The Read() deny rule itself was not abolished, but rather reverted to controlling file reads. The same release also added a /diff panel for full-screen use.
- Command-level allowed_domains: In v2.1.271, a mechanism was introduced where sandboxed auto-mode Bash, PowerShell, and Monitor declare necessary hosts to the command itself, which are then reviewed along with the command. Approved hosts are opened only during the execution of that command and do not remain in the session allowlist or configuration file. In organizations that fix the allowlist using strictAllowlist or allowManagedDomainsOnly, this declaration itself is rejected by design.
- On-demand approval for unknown hosts: In v2.1.243, network permission for sandboxed Bash changed from pre-enumeration of allowed hosts to on-demand approval at the moment of attempting to connect to an unknown host.
- Stabilization patches: In v2.1.252, issues such as Bash commands failing on some Macs, "always allow" not being saved in projects where .claude/settings.local.json had not been created, and Remote Control sessions stalling for several minutes during connection degradation were fixed.
Looking at the month as a whole, the granularity of network permissions was refined in stages, from the "when to ask" change in v2.1.243 to the design in v2.1.271 that forces explicit declaration of "which command uses which host and to what extent." On the other hand, v2.1.260 was a reminder of the side effects of over-tightening, where strict permission rules stopped daily builds and grep operations. My reading is that permission design is being adjusted to include not just "restricting" but also "not stopping business operations."
Claude Code Cost and Gateway Operations
- modelPricing and cache TTL: In v2.1.243, the management setting modelPricing allowed contract unit prices and discount rates to be reflected in /cost and telemetry cost displays. Additionally, promptCacheTtl and subagentPromptCacheTtl allow for separate cache expiration settings for main conversations and sub-agents.
- maxEffortLevel: In v2.1.267, maxEffortLevel was added, allowing organizations to enforce an upper limit on effort levels. This applies to all providers, including Bedrock, Vertex, and Foundry; users can choose levels lower than the limit, but cannot raise them beyond it.
- Accumulated prompt cache fixes: In versions v2.1.265, 267, 268, and 269, cache corruption issues with different causes for each operation—such as sub-agent resume, tool addition or model switching mid-conversation, SDK excludeDynamicSections, and automatic resumption at output limits—were individually fixed. In v2.1.266, a regression where all requests failed if CLAUDE_CODE_USE_GATEWAY was set alone was urgently patched.
- Gateway pricing: In v2.1.268, setting pricing: in gateway.yaml ensures that /cost and telemetry for signed-in clients match the spend meter on the gateway side. A change was also added to issue a warning at startup if gateway.access_control.allow_cidrs is left empty.
- plugin eval: In v2.1.269, claude plugin eval was added, allowing users to run a plugin's eval suite to score and compare results with and without the plugin loaded. Results are output in JSON and HTML reports.
- Headers for gateways: In v2.1.273, x-claude-code-* headers were added to convey request types and calling agents. This requires opt-in via CLAUDE_CODE_GATEWAY_HINT_HEADERS=1. Notifications for when an MCP server disconnects and automatic reconnection fails were also added.
Looking through the month, the three directions of "aligning displays with reality" (modelPricing, gateway pricing), "setting upper limits" (maxEffortLevel), and "reducing waste" (cache fixes) have come together under the premise of organizational use. In particular, the move to resolve discrepancies between displayed costs and actual billing from both the client and gateway sides feels like a change that will quietly but effectively benefit teams using multiple people and multiple agents.
Attacks targeting AI agents and incidents caused by agents themselves
- FSMonitor vulnerability: Research was reported showing that by using a malicious .git/config core.fsmonitor, arbitrary commands can be executed outside the sandbox the moment an AI coding agent runs a process equivalent to git status in the background. The targets include goose, Codex, Claude Code, Hermes Agent, Qwen Code, Grok Build, and Cursor, with varying levels of fixes across tools. A key feature is that this is not a bug, but an exploitation of legitimate Git functionality.
- OpenAI Hugging Face intrusion, follow-up: The root cause of the July incident was identified as "reward hacking" in OpenAI's technical report and an independent investigation by METR. The content revealed that approximately 1,200 evaluation agents used a shared namespace in the Artifactory cache in an environment that should have been isolated, creating an unauthorized message board.
- Anthropic Threat Intelligence Report: Reports included a case where a single stolen developer token led to full administrative access to a cloud environment in about 3 hours, and real-world examples of "campaign memory," where targets and credentials persist across sessions. It also outlines how stolen API keys are used for three purposes: resale, diversion of computing resources, and shifting responsibility.
- Loopjacking: Research into attack patterns targeting the human approval process itself. It includes expression-based attacks that display incomplete information on approval screens, and state-replacement attacks that rewrite arguments immediately before execution after approval. While reproduced in Agno AgentOS and LangGraph, it was reported that the OpenAI Agents SDK was not affected because it is designed to save approval content and compare it upon resumption.
What they have in common is the structure where parts assumed to be trusted—such as "the target approved," "the environment that should be isolated," and "the path the agent moves on its own"—were actually vulnerabilities. FSMonitor became an entry point for background processes not explicitly instructed by the user. The follow-up on the Hugging Face intrusion was about the legitimate function of delegating tasks to sub-agents being repurposed for other goals, while Loopjacking is about doubting the approval itself. It was a month where different entry points converged on the same lesson: "doubt your assumptions."
Agent Control and Data Protection Design
- Three-layer organization for "no-leak" design: We organized defenses for LLM agents handling sensitive data into three layers: pre-deployment build time (schema hardening, boundary sanitization, tool gating), runtime (combination of deterministic detectors and LLM-based semantic analysis), and organizational control (data classification, access control, encryption, vendor control). This is based on two research papers and a collection of controls for practical use.
- Enterprise Frontier Safeguards: A feature was released for Claude Enterprise that allows activity data used for automatic misuse monitoring to be stored in the customer's own S3, Azure Blob Storage, or Google Cloud Storage with customer-managed encryption keys. While the storage location moves to the customer, the detection logic remains on the Anthropic side. Deployment will be phased starting in the fall of 2026.
- Confidential Computing (TEE): We organized the mechanisms and performance costs of isolating LLM inference along with the hardware. In actual measurements, GPU-side overhead is reported to be less than 7% on average, and throughput overhead for CPU-side TEE is also less than 10%.
- Anthropic's R&D automation and monitoring: It was announced that 26% of the company's model R&D tasks are now at a level (AL4) where AI performs them from start to finish under human supervision. Additionally, measured values were shown for monitoring approximately 30,000 agents at all times using a two-layer approach: online monitoring before execution and offline monitoring after execution. Both are self-measured figures.
It was a month where we could see the areas to protect expanding beyond prompts and outputs to include tool arguments, handoffs between agents, storage locations for monitoring data, and the hardware of the execution environment. Also, the two-layer monitoring concept mentioned in Anthropic's R&D—"stop things immediately before execution, and monitor things that progress gradually after execution"—feels like a design that can be applied regardless of organizational scale.
BigQuery and Data Infrastructure
- JDBC driver vulnerability: A vulnerability (GCP-2026-056) involving remote code execution and privilege escalation due to insufficient validation of connection string parameters in the BigQuery Data Transfer Service JDBC driver was disclosed. Google stated that no action is required from users, as the patch was completed on May 1, 2026, and the bulletin was released after the fact.
- BigQuery Graph GA: A feature that natively integrates GQL and SQL into BigQuery, allowing existing tables to be treated as graphs, became GA on September 1, 2026. Pathfinding is said to be up to 100 times faster, and Borderless Graph Lakehouse, Chat with Graphs, Agent Graph Building Skill, and Context Graph features were also released simultaneously.
- Python UDF real-time logs: A feature to check Python UDF execution logs in real-time via Cloud Logging became GA. Combined with the Cloud Monitoring metrics (CPU, memory, maximum concurrent requests) added in Preview in April, both logs and metrics are now available.
- dbt Wizard's Explore mode: Explore mode, which allows users to ask natural language questions about governed production data and displays the underlying SQL or metric definitions for every answer, was added in Preview. Read-only users without a developer license can also ask questions from the home tab.
- pipelines unit testing: A feature for BigQuery pipelines (Dataform) that allows testing SQL transformation logic against mock datasets became GA. There is a limit of 100 rows per input, Dataform core 3.0.56 or later is required, and it can be integrated into CI via WorkflowInvocations.create.
This month's BigQuery and data infrastructure saw the arrival of both expanded capabilities (Graph) and the underlying support needed for continued use (UDF logs, pipeline testing, visualization of dbt Wizard's answer sources). There are more ways to confirm not just "that a result was produced," but "why that result was produced" and "whether anything is broken," which feels like a continuation of last month's theme that "the real work begins after you start using it."
Models and Other CLI Agent Movements
- Claude Opus 5.5: Released on September 22, 2026. At $4 for input/$20 for output (a 20% reduction each compared to Opus 5) and $0.20 for cache reads (a 60% reduction), Anthropic's internal tests show it is 40% cheaper than Opus 5 for typical workloads. It has a 1M token context, and the fact that adaptive thinking is always on and cannot be disabled is a breaking change. Claude Code has switched the default Opus to Opus 5.5 since v2.1.280.
- GPT-6 Sol/Luna: Announced on September 22, 2026, this is a high-speed, low-cost version of the GPT-6 Astra lineage. Sol is $2 input/$10 output, and Luna is $0.10 input/$0.50 output, which is nearly half the price of the previous generation (GPT-5.6 series). The claim that Sol's error rate is about half that of the previous generation is based on OpenAI's own internal evaluations.
- Real-SWE: A benchmark evaluated on private, real-world corporate codebases, where even the top-performing Fable 5.1 had a resolution rate of 38.8%. The official figures only list costs for two models, Gemini 3.8 Flash and Fable 5.1; looking at these two, the cheaper Gemini 3.8 Flash is more advantageous in terms of cost per resolved task.
- Codex CLI v0.152.0: The rate limit banner has become an actionable UI that leads directly to usage checks, credit management, and plan changes. An output_token_limit can now be set for each MCP tool, and it remains applied even after restarting the session.
- GitHub Copilot CLI v1.0.85: Vim mode is now open to all users, and GPT-6 Astra has been added as an option. In /sandbox, you can now add host-specific allow/deny rules without replacing the configured upstream proxy.
For both Anthropic and OpenAI, the new models are highlighting "price reductions" just as much as "performance improvements," and the two announcements made on the same day (September 22) showed the weight of cost as a selection criterion. The 30% range figure for Real-SWE reminds us that public benchmark rankings are different from results in one's own field. The updates to Codex CLI and Copilot CLI, like Claude Code, were aligned in the direction of reducing operational friction such as rate limits and network permissions.
Key Points
- Regarding Claude Code's permissions, from the withdrawal of the Read deny scope (v2.1.260) to per-command host review (v2.1.271), adjustments have continued to address both "being too strict and stopping work" and "being too loose and creating a hole." It is better to think of permission rules not as something you set and forget, but as something whose behavior should be checked with every update.
- Follow-up reports on FSMonitor, Loopjacking, and the Hugging Face intrusion, while having different entry points, share the commonality that the trusted premises of "approval," "isolation," and "automatic background processing" were broken. Personally, in designing AI agent permissions, being able to link and verify "who approved what" and "what was actually executed" was the most practical issue this month.
- With cost management being refined from multiple angles—"display accuracy," "enforcement of limits," and "reduction of cache waste"—the features required for distributing Claude Code within an organization are falling into place. The same trend was seen in the Codex CLI rate limit banner.
- Opus 5.5 and GPT-6 Sol/Luna were both releases that highlighted the extent of their price cuts. Since the figures are still based on in-house testing and internal evaluations, it is safe to view them with the premise of re-measuring them against your own workload.
- The GA of unit testing for BigQuery Graph and pipelines shows that the direction is moving toward completing not just "using new features" but also "verification and visualization for continued use" on the BigQuery side.
Things usable in practice
- If you are using Read() deny in Claude Code permission rules, it is worth looking back to see if builds or grep were unnaturally blocked during the period you were on v2.1.259, and checking if you have updated to v2.1.260 or later. If you are using a sandbox in auto mode, it is also safe to check how the per-command host declaration in v2.1.271 works in combination with strictAllowlist or allowManagedDomainsOnly, along with your management settings.
- If you are using Claude Code with multiple people, it is a good idea to check if modelPricing and maxEffortLevel are set, and if you are distributing via an LLM gateway, check the pricing: in gateway.yaml as well. Checking logs to see if all requests failed via the gateway between v2.1.265 and 266 is also effective.
- If you receive a repository of unknown origin via zip, shared drive, or sync folder and have an AI agent open it, it is worth checking .git/config's core.fsmonitor in advance and considering disabling it by default with git config --global core.fsmonitor false. Checking whether your primary tools are patched or unpatched comes first.
- If you are implementing and operating human-in-the-loop, it is a good idea to check if the design re-verifies that the approved content matches the content immediately before execution. For approval records, it is safer to fix not only the operation ID but also the target, arguments, and destination.
- If you are using Claude Code with the default model, it has switched to Opus 5.5 since v2.1.280, so it is safe to check how adaptive thinking being always on and the change in cache reading unit price affect your workload. If you are using the GPT-5.6 series, it is also worth looking at the price difference when switching to GPT-6 Sol/Luna and the difference in the default value for reasoning effort.
- If you are managing SQL transformations with BigQuery pipelines (Dataform), you can try adding unit tests for logic prone to errors, such as aggregations, regular expressions, and conditional branching, after confirming you are on Dataform core 3.0.56 or later. BigQuery Graph has increased the options for seeing if it suffices before considering a dedicated DB when graph-like analysis needs arise. However, since it just reached GA, it is safer to try it out on a small scale with new needs.
Summary
Although the fields ranged widely—from Claude Code permissions and costs, attacks and incidents targeting agents, data protection design, to the renewal of BigQuery and models—the underlying themes seemed to be two trends: the realization that "when operating agents in an organization, permissions, costs, approvals, and isolation are not as mechanically effective as one might think," and the development of infrastructure to "visualize that, set limits, and make it verifiable later." I would like to write a report on actual machine verification when I find the opportunity.
